# 登録ジョブと手動実行（Phase 17.1）

## 目的と構成

Workbenchで処理を名前付きジョブとして登録し、引数を渡して手動実行する。
既存のSQL、dbt、取込、WAP処理を順に呼び出し、処理ごとの成否を残す。
実行状態は `SHIROKUMA_STATE_DIR` 配下のSQLiteで管理する。追加サーバーや
外部スケジューラは不要。同じ状態ディレクトリを使うホスト内では同時に1件だけ実行する。
定期実行は [スケジュール実行（Phase 17.2）](scheduled_jobs.md) を参照する。
SQL条件による通知は [アラート（Phase 17.3）](alerts.md) を参照する。

名前、説明、引数定義、処理の順序を保存する。実行受付時に定義と引数をコピーするため、
登録内容を後から変更しても実行済み・実行中の内容は変わらない。
HTTPリクエストは受付後に返り、Workbenchで処理の進捗を確認できる。

## 権限

- 管理者とデータエンジニアは自分のジョブを登録・更新・実行できる。
- 閲覧者にはジョブAPIを公開しない。
- 管理者は全ジョブ・履歴を閲覧できる。他人のジョブの変更・実行は所有者に限定する。
- データエンジニアはSQL処理と読取専用のアラート判定を利用できる。Raw／Sandboxの書込みなど既存SQLポリシーを適用する。
- dbt、ローカルファイル取込、WAPの更新・公開は管理者だけが登録・実行できる。
- 非同期処理にも受付時の利用者・選択ロールを明示して渡す。管理者権限への自動昇格は行わない。
- 共有モードでは各処理の直前にアカウントの存在と権限を再確認する。

ローカル管理者モードの所有者名は `local`。資格情報そのものはジョブに保存しない。
SQLの結果行は履歴に保存せず、成否と処理件数などの要約を記録する。
SQLは結果取得上限で打ち切らず、全ページの処理完了を確認する。
Trinoの失敗は安全なエラー識別子を表示し、データ値を含み得る生のメッセージは台帳に保存しない。
定義と引数はローカル台帳に残るため、パスワードやAPIキーを引数として渡さない。

## 利用方法

Workbenchの「ジョブ」で名前、説明、引数定義、処理を入力して保存する。
保存後に実行引数を入力して「ジョブを実行」を選ぶ。
実行履歴から各処理の開始・終了時刻、結果、失敗箇所を確認する。

利用できる処理は `sql`、`alert`、`dbt_build`、`dbt_test`、`ingest`、
`wap_refresh`、`wap_publish`。取込先やファイルパス、WAP対象表は登録時に固定する。
dbtは既存の `dbt_persistent` プロジェクトを実行する。
任意のPython、シェルコマンド、外部APIを実行する入口は設けない。

引数は `string`、`integer`、`boolean`、`date` に対応する。
SQLでは `{{引数名}}` を値の位置に置き、引用符では囲まない。
文字列連結によるSQL作成やテーブル名の置換には使わない。
引数の型・不足・余剰と全処理の定義を、最初の処理を実行する前に検証する。

```json
{
  "name": "count_orders",
  "description": "指定した日付を添えて受注件数を確認する",
  "parameters": {"as_of": {"type": "date", "required": true}},
  "steps": [
    {
      "name": "受注件数の確認",
      "action": "sql",
      "sql": "SELECT {{as_of}} AS as_of, count(*) FROM iceberg.marts.fct_orders",
      "mode": "read-only",
      "schema": "marts"
    }
  ]
}
```

上記の実行引数は `{"as_of":"2026-10-18"}`。日付はSQLの日付値として扱う。

## HTTP API

既存Workbenchの認証・ロール選択・同一オリジン制限を利用する。
利用者名や実行ロールをリクエスト本文で指定することはできない。

| 操作 | メソッド・パス | 入力／応答 |
|---|---|---|
| 一覧 | `GET /api/jobs` | `{"jobs":[...]}` |
| 登録・更新 | `POST /api/jobs/save` | ジョブ定義／`{"job":...}` |
| 手動実行 | `POST /api/jobs/run` | `{"name":"count_orders","arguments":{"as_of":"2026-10-18"}}`／202と実行ID |
| 履歴 | `GET /api/jobs/runs` | `{"runs":[...]}` |
| 実行詳細 | `POST /api/jobs/detail` | `{"run_id":"..."}`／`{"run":...}` |

実行中の受付競合は409、入力不正は400、権限不足は403、見つからない実行は404。

## 停止・失敗と再実行

処理は順番に実行し、一つ失敗したら後続を実行しない。
実行権の取得と台帳への受付記録はSQLiteのトランザクションで行い、
別Workbenchプロセスからの同時受付も拒否する。
実行中は状態ディレクトリ内の実行ロックを保持する。
ロックを失った未完了実行は、次の一覧・詳細取得や実行受付で「結果不明」にする。

SQLの反映とローカル台帳の更新を、単一のトランザクションにはできない。
実行中断時に反映先を確認せず自動再実行すると二重取込になり得るため、自動再試行はしない。
結果不明の場合は、成功済み処理と反映先を確認してから新しい実行を開始する。
成功済みの処理を含む一括ロールバックや、障害をまたぐexactly-onceは保証しない。

WarehouseのWakeとAuto-Chill調停は既存処理を利用する。
各操作の既存タイムアウトに加えて処理の境界で900秒の実行時間を確認するが、
実行中のPythonスレッドやSQLを一律に強制停止する期限ではない。

既存のバックアップには `jobs.sqlite3` の整合したスナップショットも含める。
ジョブ台帳の復旧先は空の状態ディレクトリに限定し、既存台帳への上書きを拒否する。
復旧後、未完了の実行はロックがないため「結果不明」となり、自動再実行されない。

## 検証

入力型、安全なSQL引数、呼出者権限、定義の保存、実行スナップショット、
同時受付、途中失敗、ロック喪失、API認証・所有者境界を自動テストで確認する。
`make verify` にジョブのテストを含める。実機検証は既存と同じく
`SHIROKUMA_RUNTIME_TESTS=1` で明示実行する。

2026-10-18、専用ローカルラボで以下を確認した。

- `make verify`：成功。Python 538件中528件成功、実機用10件は通常実行ではスキップ。Go・設計・セキュリティ検査も成功。
- 実機用10件を別途実行し、全件成功。登録ジョブ4件に加え、既存の権限境界3件・データ整合性3件の回帰を含む。
- ジョブの実機検証：取込→引数付きSQL、引用符を含む値の保持、複数行結果の件数集計、SQL失敗後の後続停止、データ作成者の実権限制限、既存dbtテストを確認。
- 自動テスト：SQLの後続ページでのエラー検出、結果行の非保持、安全なエラーコード保存、SQLiteの稼働中バックアップと既存台帳への上書き拒否を確認。
- Chrome：日本語画面で登録・再読込後の永続化・日付引数による2処理の手動実行・処理別成功履歴を確認。閲覧者のメニュー非表示、データ作成者の操作制限も確認。
- 独立したコードレビューで見つかった権限失効時の状態分類と復旧台帳の上書き競合を修正し、最終レビューでは追加指摘なし。
