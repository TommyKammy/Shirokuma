# DB-P6-2 logical read-only Queryの限定復旧契約

2026年10月29日。cold SQLの実機検証でUNKNOWNが1件発生した。通常のGET-only照合は一致するbackend終端記録を得られず、UNKNOWNを維持した。旧単一Container用recoveryを現在のcoordinator＋workerへ転用しない。

追加は既存private operator `recover-query-*` へのlogical_v1 adapterに限定する。通常HTTPへ強制閉鎖やUNKNOWN無視のflagを追加しない。現在のP認証、同一actorのstandalone read-only UNKNOWN、元のfull context／grant／binding／generation、Query owner lease、operator／exclusive lifecycle gate、他の未解決work不在を既存QueryRecoveryで照合する。SQLの再送とQuery結果の書換えを禁止する。

adapterは封印済みlogical foundationと登録probeを使い、単一の信頼済みColima Docker Engineに全compute Podが配置されている構成だけを扱う。coordinatorと設定された全worker、Deployment／ReplicaSet／Pod／Node UID、Service endpoint、image／mount／runtime configuration、実Container ID・開始時刻・restart policy・実processを照合する。namespace内およびEngineに同じ基盤の未包含Trino実行主体があれば拒否する。旧adapterの「受付時から同じContainerだった」という証明をcold受付へ流用せず、現在の基盤内の全実行主体をoperatorが確定して停止する証明として記録する。分散Node、外部worker、未知のbackend、writeや親DataOps／JobのUNKNOWNは対象外とする。

plan／intent digest／revisionの照合後、既存状態機械でDRAININGと停止intentを先に永続化する。対象の正確な旧Container群だけを停止し、それぞれの停止済みinspect、または同じEngine・ID・labelsの正のdie／destroy eventを得る。不在・timeout・新backendのreadinessだけでは証明しない。全員分の正の証拠を削除より先に保存し、既存closure transactionで対象admissionだけをFENCED_READ_ONLYにする。QueryのUNKNOWN・元SQL・元contextは保持する。

元Deploymentのdesired replicasは変更せず、Kubernetesによる置換後の新Container群と同じfoundation／pins／完全engine probeを検証し、他のblockerがなければ同じoperationのdrainを解除する。保存証拠後に停止を再送しない。中断時は同じoperationをinspect／reconcileし、証拠未回復ならDRAININGを保持する。部分停止は未停止の同じ旧Containerだけを明示applyで続行でき、reconcileは停止を行わない。

停止順序はcoordinatorを先にし、その正の停止証明を確認してからworkerを停止する。先にworkerを置換して旧coordinatorが新workerへ仕事を渡す窓を作らない。現在の全membershipを再照合し、未包含のpeerを拒否する。置換memberは旧coordinatorの停止証明以後に生まれ、同じsealed基盤に属すると確認できる場合だけ許す。欠落・不明なmemberを現在の新IDへすり替えて停止しない。各stop／removeの直前にも現P権限を照合し、legacy HISTORICAL selectorはlogical adapterへ流さない。

未計画のPod UIDはPod作成時刻もcoordinator fence後に限定する。同じ元PodのContainer置換は、元Containerの正の停止証明に加え、保存restartCountから1回だけの遷移と現在の開始時刻を照合する。Podがfence前に生まれて途中の実行主体が不明な場合や、複数回の未包含restartは拒否する。現在のContainerの開始がfence後という事実だけでは、以前の未包含実行主体を証明しない。

同じEngineには旧`shirokuma-dev`の独立coordinatorも稼働している。imageの一致だけを同じ基盤への所属と扱わない。別namespaceのactorは、Pod／Container／Node／owner chainと実mountを照合し、実際の固定`config.properties`がConfigMapと一致し、単独coordinator・coordinator内実行・loopback discovery・隔離Pod networkと確認できる場合だけ対象外とする。実fileの照合は固定pathへのDocker Archive GETで行い、container execやfileの書換えを行わない。全inventory passでこの分離を再検証し、対象基盤のruntime-node/IP censusは厳密に維持する。foreign worker・同じnamespace／foundationの追加actor・設定や正体が曖昧なactorは引き続き拒否し、別環境を停止対象へ追加しない。
