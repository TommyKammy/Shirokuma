# Workbench UI デザイン規則（2026-10-18 改修）

Workbench（`tools/local_experiment/workbench/index.html`）の画面構成と共通部品の規則。
外部CDN・フォント・ビルド基盤は使わず、HTML・CSS・JavaScriptの単一ファイルで配信する。
API契約と実行の意味は変えていない。画面の非表示・無効化は操作の案内であり、権限はサーバーが検証する。

## 画面構成

| 領域 | 内容 |
| --- | --- |
| ヘッダー | 製品名・環境、ウェアハウス状態と起動／休止、ロール、AI設定（管理者）、言語 |
| ナビゲーション | データを扱う（SQL・取り込み・データ変換・ジョブ・AI Bears）／カタログ／監視・管理 |
| ページ見出し | 見出し・1行説明・ページ単位の操作を同じ行に置く |
| ページ内ビュー | 取り込み＝ファイル・ステージ、データ変換＝モデル・更新対象、ジョブ＝ジョブ・実行履歴・通知 |

ジョブ・ステージ・更新対象は同じ流れに揃える。

1. 一覧：名前、所有者、自動実行の状態と次回予定、直近の結果を表示し、選択行を強調する。
2. 詳細：左に定義（保存）、右に今すぐ実行と自動実行（保存・停止）を置く。
3. 結果：実行後は状態を表示し、実行履歴とステップ詳細へ移動できる。

未保存の定義がある間は手動実行を無効にし、保存済みの版だけを実行する。
手動実行の結果は送信時のジョブ・選択・ロールに結び付け、応答前に対象を変えた場合は新しい選択へ表示しない。
受理済みの実行は履歴に反映し、表示上の都合で「実行失敗」と扱わない。結果の「実行詳細を表示」はその実行IDで開く。
実行履歴は閲覧できる直近100件だけを取得するため、見つからない場合は「直近100件に履歴なし」と表現する。
「実行詳細を表示」で履歴の絞り込みを戻す際は、同じ実行IDが選択済みでも一覧を再描画し、絞り込み・行・詳細を揃える。

## SQLワークシート

- 広い画面は探索・エディター・結果を並べる。1024px以下はエディター、折りたたんだ探索、結果の順に積む。
- 390px程度ではエディターを短くし、実行ボタンをエディター直下に置く。長いSQLは内部スクロールと高さ調整で編集する。
- Database mode（UX-D1）では共通ツリーの単クリックは詳細表示であり、SQL名の挿入・新しいSQL・実行先の変更は詳細の明示ボタンで行う。
  旧形式（Database mode以外）の探索だけが「選ぶとカーソル位置に名前を挿入」の動作を残す。
- Database modeの配置（2026-10-20、UX-D1モックに整合）：左は検索・更新→Database／Schema／Tables・Views（種類アイコン）→探索コンテキスト。
  作業領域は「詳細／ワークシート」の1本のタブ列、詳細はパンくず・名前・SQL名・主操作（新しいSQLを主ボタン）、
  ワークシートは実行コンテキスト（DB／Schema／実行role／mode／Warehouse／最大行数）をエディター上、取消と実行を下に置く。
  履歴の復元は結果の下にあり、1024px以下では探索を上部の折りたたみ行にする。記録は [UX-D1探索・SQL記録](database-ux-d1-explorer-sql-report-2026-10-20.md)。
- 各タブ右側の × はローカルのワークシートとその SQL を削除する。最後の1枚は理由を添えて無効化する。
  空欄と既定の注文サンプルそのものだけは直接閉じ、それ以外は保存済み SQL も含め削除確認を出す（編集履歴は持たない）。
- アクティブなタブを閉じると右隣、右がなければ左隣へ移る。他のタブを閉じても編集中の SQL と選択範囲を保つ。
  削除とアクティブIDを既存のローカル保存へ反映し、追加名は残っている番号の最大値から採番する。
- Copilot の生成 SQL は開始時のワークシートが残り SQL が変わっていない場合だけそのシートへ保存し、削除・編集後も生成結果は表示する。

## Data Engineer Bear

操作ごとに必要な入力だけを表示し、送信内容にも現在の操作の項目だけを含める。非表示の入力は無効化し、下書きは保持する。

| 操作 | 表示する入力 | 送信する項目 | ボタン |
| --- | --- | --- | --- |
| generate | 説明、SQL（任意・優先） | `request`、`sql` | SQLを生成 |
| stage | 説明、SQL、サンドボックスのテーブル名 | `request`、`sql`、`stage_table` | ステージングして検証 |
| publish | 公開するサンドボックスのテーブル | `publish` | テーブルを公開 |
| refresh | 更新するWAPモデル、SQL（任意、空欄は保存済みSQL） | `refresh`、`sql` | テーブルを更新 |
| rollback | 戻すテーブル、スナップショットID（数字のみ・文字列で送信） | `rollback`、`snapshot_id` | 指定スナップショットへ戻す |

すべて `bear: data` と `action` を明示する。選べる操作はサーバーと同じく閲覧者がgenerate、データ作成者がgenerate・stage、
管理者が全操作。登録済みの更新対象はデータ変換画面からのみ更新でき、サーバーが拒否する。
実行待ち中もボタンは無効のままにし、成功・失敗後は現在の操作とロールに合わせてフォームと実行ラベルを同期する。

## 共通部品

- **トークン**：色・余白・角丸・文字サイズは `:root` の変数だけを使う。暗い配色も変数で切り替える。
- **文字**：本文13px、表12〜12.5px、見出し20px／14px。識別子・SQL・データは等幅。
- **ボタン**：通常（補助）、`primary`（保存・確定）、`run`（今すぐ実行）、`stop`（自動実行の停止）、`danger`（削除）。
  1つの領域で `primary` は1つまでにする。
- **状態表示**：`badge`／`status-line` に `tone-ok`・`tone-run`・`tone-warn`・`tone-bad` を付ける。
  色に加えて記号（✓・●・!・✕）と文言で状態を示す。
- **メッセージ**：失敗は `error`（原因の全文）、要確認・復旧案内は `callout warn`、補足は `callout info`／`help`。
  重要な失敗や復旧案内は一時表示にせず、対象の近くに残す。
- **空・読込**：空の一覧には最初にできる操作を書く。読込中は対象の場所に「読み込み中…」を出す。
- **表**：見出しを固定し、横長の表は表の中だけを横スクロールする。NULLは斜体で区別する。

## 自動実行（スケジュール）

ジョブ・ステージ・更新対象で配置と用語を揃える。

- 上段の状態欄：有効／無効、実行方式、次回予定（タイムゾーン付き）、前回の状態、停止ボタン。
- 下段のフォーム：実行方式に必要な項目だけを表示し、有効化のチェックと「スケジュールを保存」で確定する。
- 停止は保存済みの予定だけを無効にする。フォームが未保存・不正でも停止でき、編集中の値は保存も破棄もしない。
- 一定間隔の次回予定はブラウザのタイムゾーン、カレンダー予定は指定したタイムゾーンで表示する。表示だけで予定計算は変えない。
- 更新対象で結果不明が残る間は、状態欄より先に復旧手順を表示し、手動更新の成功まで有効化を許可しない。

## アクセシビリティ

- ナビゲーション・ページ内ビュー・検査タブは矢印キー、Home、Endで移動する。フォーカス枠は常に表示する。
- すべての入力にラベルを付ける。状態の変化は `role="status"`、失敗は `role="alert"` で通知する。
- 動きは実行中表示だけにし、`prefers-reduced-motion` で止める。
- API・ユーザー入力は `textContent` で表示し、HTMLとして解釈しない。

### Databaseモードの手動DataOps（2026-10-20、P3-5）

- 手動Ingestは入力bytesと型付きpreviewを固定し、明示modeと作成先／既存Tableを確認して実行する。入力やcontextを変更した場合は再previewが必要。
- 手動WAPは独立したDB／Schema／roleを持ち、model版・build・audit・publicationを表示する。publish／rollbackはadminに限定し、role切替後は許可済みmetadataを明示的に再取得する。
- Explorerの実TableにCSV／JSONLのSnapshot固定Exportを提供する。receiptとdownloadは取得時に再認可し、grant失効後の結果・fileを表示しない。View全件ExportとWorksheet結果保存等の未対応入口は無効を維持する。
- 各DataOpsパネルと受付済みoperationは元contextを保持し、WorksheetのSQL／DB／Schema／保存role／Warehouse／modeやExplorer選択を変更しない。応答不明は元の同一keyで明示照会し、別identityへ切り替えて回復しない。
- 通常CLI・3DBの実engine・実ブラウザーの正負証拠と残件は、[P3-5受入報告](database-p3-5-normal-entry-acceptance-report-2026-10-20.md)を参照。所有者の最終操作性評価はPhase 5に残す。
