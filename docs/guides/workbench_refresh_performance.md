# Workbench 状態・ジョブ・ステージ取得の改善

検証日: 2026-10-19。変更前の基準: `374a9dd5`。

## 実装範囲

- `/api/status` は Kubernetes の `deploy,sts` を1回取得し、Warehouse と各コンポーネントの状態を計算する。既存の CLI の状態取得と同じ純粋関数を使い、起動・休止は行わない。
- ブラウザーは同じロール・セッション・世代の進行中の状態取得だけを共有する。完了結果の時間キャッシュは設けない。通常・ヘッダー双方の起動／休止と自動Chill設定変更では、変更前の応答を無効にして変更後の状態を取得する。
- ジョブ画面の初期更新でスケジュール一覧を1回だけ取得する。選択済み実行の詳細は、その更新で取得した実行一覧に含まれる場合に再利用する。一覧外の実行や直接選択では詳細APIを使う。
- ジョブ定義一覧と実行履歴は要求番号を分け、履歴の定期更新が保存後の定義取得を打ち消さないようにする。ロール・画面世代・選択の変更後に返った古い応答も反映しない。
- ステージ保存後の重複一覧取得を取り除く。既存の最新設定・所有権・設定版の再照合と、プレビュー／ファイル／出力情報の無効化は維持する。

新しい依存、常駐サービス、永続キャッシュは追加していない。定期確認の頻度、監査履歴、自動Chillの二重判定解消は今回の対象に含めない。

## 実画面での変更前後

同じホストのローカル Workbench を管理者ロールで操作し、ブラウザーの Network イベントから通信を測定した。時間はAPI応答ヘッダー到着までの値で、画面全体の描画完了時間ではない。ジョブ実行、テーブルへの取込、Warehouseの休止は計測中に実施していない。

| 操作 | 変更前 | 変更後 | 確認結果 |
| --- | --- | --- | --- |
| 状態更新・5回 | 80 / 81 / 83 / 76 / 90 ms、中央値81 ms | 51 / 49 / 46 / 42 / 43 ms、中央値46 ms | 中央値で約43%短縮。サーバーのKubernetes取得も2回から1回へ |
| ジョブ画面を開く | jobs → schedules → runs → alerts → schedules、5通信 | jobs → schedules → runs → alerts、4通信 | スケジュールの二重取得を除去 |
| 詳細選択済みの実行履歴更新・3回 | runs → detail → alerts → schedules、毎回4通信 | runs → alerts → schedules、毎回3通信 | 詳細表示を保ち、重複取得を除去 |
| ステージ保存・3回 | save → stages → stages → files、毎回4通信 | save → stages → files、毎回3通信 | 保存後の最新一覧は1回取得し、ファイル表示も成功 |

ジョブの各通信は前後とも概ね1〜2 ms。ステージ保存は3 ms、後続通信は前後とも2〜3 msだった。これらの効果は通信本数の削減として確認でき、体感速度の大幅な改善とは断定しない。測定は少数回であり、他のホストや負荷条件の保証値ではない。

別途、確認用タブに1秒の通信遅延を設定し、Computeの更新ボタンと画面選択を重ねたところ、状態取得は1通信にまとまり、完了後に更新ボタンが再び有効になった。計測後は遅延設定を解除した。

## 権限・更新時の整合性

ローカル稼働環境の読取APIで、既存のロール制限を確認した。

| ロール | status | jobs | stages |
| --- | --- | --- | --- |
| admin | 200 | 200 | 200 |
| data_engineer | 200 | 200 | 403 |
| bi_viewer | 200 | 403 | 403 |

- 実画面で管理者→閲覧者→データ作成者→管理者を切り替え、管理者へ復帰した。
- 専用CSVのプレビュー後にステージ設定を変更すると、古いプレビューは破棄され、保存前の実行操作が無効になることを確認した。保存後もファイルの再選択・再確認が必要だった。
- 検証専用ステージとCSVは後片付け済み。テーブルへの取込や自動取込スケジュールの登録は行っていない。
- 後片付け後のステージ一覧が空に戻ることと、確認用ブラウザーのコンソールエラーが0件であることを確認した。
- 自動テストで同時取得の共有、失敗後の再試行、ロール変更往復・セッション変更、変更前の遅延応答の破棄、スケジュール入力保持、詳細取得のフォールバック、保存後の設定版・操作権限の再照合を確認した。
- Trinoの欠落、取得失敗、他コンポーネントの未準備状態でも、既存のエラー／degraded表現を維持する。認可は取得処理より前に行う。
