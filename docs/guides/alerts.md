# アラート（Phase 17.3）

## 構成と使い方

[登録ジョブ](registered_jobs.md)の処理に「アラート判定」を追加し、
読取専用SQLが `TRUE` を返したときにWorkbenchへ通知を残す。
手動実行でも、既存の[スケジュール実行](scheduled_jobs.md)でも同じ処理を使う。
通知は既存の `SHIROKUMA_STATE_DIR/jobs.sqlite3` に保存し、新しい常駐プロセスや依存ライブラリは追加しない。

ジョブ画面で条件SQL、通知メッセージ、重要度（警告／重大）を設定する。
SQLは必ず1行1列の真偽値を返す。`TRUE` は要確認、`FALSE` は条件解消を意味する。
たとえば欠損のある受注を検知する場合は、次のジョブを登録する。

```json
{
  "name": "orders_quality",
  "description": "受注金額の欠損を確認する",
  "steps": [{
    "name": "金額の欠損",
    "action": "alert",
    "schema": "marts",
    "sql": "SELECT count(*) > 0 FROM iceberg.marts.fct_orders WHERE total_amount IS NULL",
    "message": "受注金額が未入力のデータがあります。内容を確認してください。",
    "severity": "warning"
  }]
}
```

テーブル・列名は利用するデータに合わせる。SQLの型付き引数は通常のジョブと同様に使える。
メッセージは1〜500文字の固定文、重要度は `warning`（既定）か `critical`。
`mode` の指定は受け付けず、常に読取専用で実行する。

`NULL`、数値、文字列、0行、複数行・列、取得打切り、SQLエラーは判定失敗となる。
その場合は既存通知を解消せず、ジョブを失敗として後続処理を止める。
`TRUE` による通知の発生自体は成功した処理であり、通常の後続処理は続く。
通知を条件に後続処理を分岐する機能は設けない。

## 通知の状態

ジョブ画面の通知一覧とメニューの未確認件数で確認する。
既存の画面更新周期に合わせて取得するため、表示まで最大約15秒かかる。
一覧は未確認を優先して最大100件を表示し、件数は表示外も含む。
確認すると、次の古い未確認通知も表示される。

| 判定・操作 | 通知の変化 |
|---|---|
| 初めて `TRUE` | 未確認の通知を1件作成 |
| 同じ異常が続いて `TRUE` | 同じ通知の最終検知時刻と回数を更新 |
| 「確認済みにする」 | 確認者・確認時刻を保存。条件の継続状態は変えない |
| 確認後も `TRUE` | 未確認へ戻さず、同じ通知を更新 |
| `FALSE` | 継続中の通知を条件解消として終了 |
| 解消後に再び `TRUE` | 新しい未確認通知を作成 |
| 判定失敗 | 以前の状態を保持。実行履歴に失敗を記録 |

「確認」と「解消」は独立している。未確認のまま条件が解消した通知も未確認件数に含む。
同一性はジョブ・処理位置・判定定義・型付き実行引数で判断するため、異なる日付などの引数は別の対象になる。
別の引数で `FALSE` が返っても、以前の引数の通知は解消しない。

条件SQL、メッセージ、重要度、処理名、スキーマ、引数定義の変更や処理の削除・並べ替えにより、
該当する旧通知は「定義変更により終了」とする。正常化による解消とは区別する。
古い定義の実行が後から完了しても、変更済みの通知を再生成しない。
説明文など判定と無関係な変更では通知を終了しない。

## 権限と保存

管理者とデータ作成者が利用でき、SQLの既存権限制限を引き継ぐ。閲覧者には公開しない。
所有者だけが自分の通知を確認できる。管理者は全所有者の通知を閲覧できるが、他人の代わりに確認はできない。
API本文から利用者・ロールは指定できず、認証された利用者と選択ロールを使う。

条件の結果行は保存しない。通知には固定メッセージ、重要度、発生・最終検知・解消・確認時刻、
回数、関連実行IDを保存する。ジョブ詳細には真偽の判定と通知ID・状態を記録する。
通知の更新と処理成功の記録は同じSQLiteトランザクションで確定する。
既存バックアップに通知・確認状態も含まれ、復元後のスケジュールは従来どおり無効となる。

| 操作 | API | 入力／応答 |
|---|---|---|
| 一覧・未確認件数 | `GET /api/alerts` | `{"alerts":[...],"unacknowledged_count":1}` |
| 確認 | `POST /api/alerts/ack` | `{"alert_id":"..."}` ／ `{"alert":...}` |

## 実行上の制約

定期判定はWorkbenchサーバーの稼働中だけ行う。ホスト停止・スリープ中の実行や、
競合・遅延でスキップした判定を後から補完しない。
したがって異常の検知を一定時間内に保証する監視サービスではない。
外部通知、OS通知、Webhook、自動修復、再通知間隔、通知保持期限はこの段階では追加しない。
通知履歴はローカル台帳に蓄積する。
