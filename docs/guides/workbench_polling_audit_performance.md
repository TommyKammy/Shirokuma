# Workbench マート・監査ログ・自動Chillの通信軽量化

検証日: 2026-10-19。変更前の基準: `7ea47d11`。

## 実装範囲

- マート一覧の画面ポーリングは、実行が `queued` / `running` なら2秒、実行中の処理がなく有効なスケジュールだけがある場合は15秒とする。それ以外は停止する。非表示・画面移動・ロール変更後の応答排除と、編集中フォームの保護を維持する。
- 監査画面のPawprintsとロード履歴は、同じ `/api/pawprints` の最新100件から描画する。ロード履歴の対象操作とフィルターは従来通りとする。
- Trino履歴は `/api/history?mode=runtime` で独立取得する。このモードはAgentHouseを取得しない。指定なしの `/api/history` は従来の応答を維持する。Trinoの応答待ちや失敗がPawprintsの表示を妨げない。
- 監査取得は、同じロール・セッション・世代の進行中リクエストだけを共有する。完了結果の時間キャッシュは設けない。ロール・セッション変更時は旧表示を消し、監査画面を開いていれば即時再取得する。旧処理でボタンが無効になっていても再取得できる。
- ブラウザーから15秒ごとに送っていた自動Chillの判定POSTを削除する。既存のサーバー側15秒監視、管理者の設定変更、状態表示、設定の永続化、起動・終了処理、安全確認は維持する。既存の明示的な `check` APIも互換性のため残す。

サーバーのジョブスケジューラ、次回実行日時計算、停止中の扱い、実行の重複防止・復旧処理には変更を加えていない。新しい依存・常駐サービス・永続キャッシュは追加していない。自動Chillの一本化は通常のWorkbenchブラウザーとサーバー間の重複解消であり、ホスト上の全プロセスを束ねる新しい監視機構は導入しない。

## 実画面での変更前後

同じホストのローカルWorkbenchを管理者ロールで操作し、ブラウザーのNetworkイベントから測定した。ポーリングは30秒の固定窓、監査表示は画面を開き直す操作を3回測定した。API時間は応答ヘッダー到着まで、転送量はHTTPヘッダー込みの値であり、画面全体の描画完了時間ではない。

| 対象 | 変更前 | 変更後 | 効果 |
| --- | --- | --- | --- |
| 実行待ちマートの一覧取得・30秒 | 15回 | 2回 | 約87%減 |
| 自動Chill有効時のブラウザー判定POST・30秒 | 2回 | 0回 | ブラウザーからの定期判定を除去 |
| 監査表示1回のAgentHouse取得 | 2回 | 1回 | 重複問い合わせを除去。バックエンド呼出経路とテストでも確認 |
| 監査表示1回の合計転送量 | 116,047 bytes | 68,980 bytes | 約41%減 |

監査表示のHTTPリクエスト本数自体は2本のまま。PawprintsとTrinoを独立させ、同じ監査データを2回取得・転送する部分を取り除いた。最新100件の表示、ロード履歴15件、管理者のTrino履歴1件が実画面に表示された。テスト等で最新イベントの内容はわずかに変わっているが、前後ともPawprintsは100件だった。

| API | 変更前3回 | 変更後3回 |
| --- | --- | --- |
| Pawprints | 9 / 10 / 8 ms、各67,665 bytes | 9.642 / 16.356 / 12.833 ms、各67,646 bytes |
| 履歴 | 82 / 80 / 144 ms、各48,382 bytes | runtimeのみ134.434 / 63.217 / 72.948 ms、各1,334 bytes |

履歴時間の中央値は82 msから約73 msだったが、変動範囲が重なるため体感速度の大幅改善とは断定しない。今回の確実な効果は待機時の通信本数・重複問い合わせ・転送量の削減である。PawprintsはTrinoの完了を待たず描画される。

ポーリング測定には、2099-01-01 00:00 UTCの1回予約を持つ一時マートを使用した。実行・テーブル作成は行わず、実行履歴0件を確認した。自動Chillは元の無効設定から一時的に60分へ変更し、測定中はWarehouseを休止させていない。実行中2秒ポーリングは制御したJavaScriptテストで確認した。

定期更新が混ざった監査サンプル、および実画面で発見した入力検査不整合による403応答は性能比較から除外した。`mode` を `/api/history` だけで受け付ける修正と認可経路のテストを追加し、上表はすべて修正後のHTTP 200応答から算出した。

## 権限・整合性・再起動

| ロール | runtime履歴取得 | マート一覧 | 自動Chillの設定変更 |
| --- | --- | --- | --- |
| admin | 200 | 200 | UIで成功 |
| data_engineer | 200 | 403 | 403 |
| bi_viewer | 200 | 403 | 403 |

ローカル稼働APIで上記を確認した。互換用の明示的なChill判定は従来通りdata_engineerで200、bi_viewerで403だった。認証情報と選択ロールの上限、未知のクエリ引数、不正・空・重複した `mode` の拒否は、実際の認可処理を通すテストで確認した。

実画面でdata_engineer → bi_viewer → adminと切り替えると、それぞれPawprintsとruntimeを1回ずつ即時取得し、200応答で表示が更新された。非管理者では当該ロールのTrino履歴は0件、管理者に戻すと1件だった。古い応答の到着順・旧ボタンが処理中の状態・同時更新の共有は制御したJavaScriptテストで検証した。修正後の検証タブにブラウザー警告・エラーはなかった。

Workbenchを通常停止・再起動し、次の点を実環境で確認した。

- 自動Chillの60分設定が復元され、Warehouseはactiveのまま。
- 一時マートの `next_run_at` は `2099-01-01T00:00:00+00:00` のままで、不要な実行は発生しない。
- 終了時に一時予約を無効化し、実行履歴0件を再確認して、既存のロックと原子的保存を使って一時登録と対応する予約だけを除去。他の登録・予約が変わっていないことを照合。
- 自動Chillを元の0分（無効）へ復元。再起動後も0分、一時登録なし、Warehouse activeを確認し、Workbenchを起動した状態で終了。

実際のアイドル閾値到達によるWarehouse休止や、実ジョブを実行中に止める破壊的な試験は行っていない。サーバー監視の起動・終了、設定再読込、実行中クエリの保護、同一プロセスでの監視スレッド重複起動防止、ジョブ・マートのスケジュール／復旧は既存および追加の自動テストで確認した。
