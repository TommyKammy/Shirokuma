# 登録マートの定期確認・自動更新（Phase 19.2）

## 範囲

[登録マート](managed_marts.md) に監視テーブルと予定を設定し、データ変更時だけ全件更新する。
既存のWAP・ジョブ実行器・SQLiteスケジュールを再利用し、サービスや依存ライブラリは追加しない。
増分計算、依存関係の自動解析、マート間の順序制御、鮮度の保証は対象に含めない。

監視対象は `iceberg.raw.<table>` または `iceberg.staging.<table>` のIceberg実テーブルを明示する。
1つ以上の監視テーブルが自動更新に必要。監視対象なしの既存定義は手動更新を続けられる。
SQLが読む入力を自動推測しないため、監視対象は利用者が選ぶ。
未指定の入力、外部システム、現在時刻に依存する式、スキーマだけの変更は検知対象外とする。
公開先への直接変更も監視しない。これらを反映・修復する場合は手動更新を使う。

## 操作

管理者がWorkbenchの「データ変換」で更新対象を選び、監視テーブルを保存する。
続いて定期確認の予定を保存・有効化する。登録・予定保存だけではSQLを実行しない。
間隔・1回・日次・曜日・月次／月末は既存の[共通スケジュール設定](calendar_schedules.md)を使う。
「更新対象を更新」は従来どおり強制的な手動全件更新で、監視の基準も更新する。

## 変更の判定と公開

予定を受け付けたジョブが、各監視テーブルの現在のスナップショットIDを読む。
前回の公開成功時の基準と同じなら「変更なし」と記録し、WAPの構築・監査・公開は行わない。
基準がない初回、またはどれか1つでも異なる場合は、保存済みSELECTを既存WAPで全件更新する。
スナップショットIDは大小で比較せず、ロールバックも変更として扱う。

基準には更新開始前に取得したIDを使い、公開成功を確認した後で保存する。
更新中に入力が変わった場合、後から取得したIDで処理済みにせず、次の確認で再検知できるようにする。
複数入力を同一時点で読むトランザクションは保証しない。
監視先の削除、アクセス失敗、Iceberg以外、現在スナップショットがない場合は確認失敗とする。
「変更なし」の成功は公開成功日時を進めない。

スナップショットの意味はTrinoの[Icebergメタデータテーブル](https://trino.io/docs/current/connector/iceberg.html#metadata-tables)に従う。

## 権限・停止・復旧

- 設定・実行は登録した管理者本人に限定し、受付時と実行時に権限を確認する。
- 予定は登録定義の版に結び付ける。定義編集時は予定を停止し、検知の基準を無効化する。
- 既存の全体1ジョブ制限を維持する。予定の重複受付を防ぎ、競合・60秒以上の遅延は待たずにスキップする。
- 更新失敗・結果不明では予定を停止する。品質不合格で公開済みデータと以前の基準を保持する。
- 結果不明は、明示的な手動更新が成功するまで自動更新を再開できない。
- 公開・基準保存・実行履歴は別々に確定する。後段の失敗では公開や基準保存が済んでいる場合もあるため、
  結果不明を「未実行」と扱わず、手動更新の成功で再確認する。
- 停止は新規受付を止める。受付済みの処理は中断せず、完了結果を履歴に残す。
- Workbench停止中・ホストのスリープ中は動作しない。再起動で過去の予定をまとめて実行しない。
- 実行時には休止中のウェアハウスを起動する。変更確認も計算資源を使うため、必要な間隔で予定を設定する。
- 定義と基準は既存WAP台帳、予定と実行履歴は既存SQLiteに保存する。バックアップ復元時は予定を無効化する。

## API

`POST /api/marts/save` に省略可能な `watch_tables` 配列を追加する。
`GET /api/marts` は監視テーブル・予定・直近の確認結果と公開成功日時を返す。
`POST /api/marts/schedule` は `name`・`enabled` と共通スケジュール設定を受け取り、
有効化時は登録定義の `version` が必要。`{"name":"sales","enabled":false}` だけでも停止できる。
保存結果は `schedule` に返す。既存の手動更新APIとジョブ履歴をそのまま使う。
