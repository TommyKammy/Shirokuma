# 登録マートの手動更新（Phase 19.1）

## 範囲と構成

SELECTと品質条件を更新対象として登録し、WorkbenchのTransformation画面から全件更新する。
登録と実行を分け、登録だけではクエリ・テーブル作成・ウェアハウス起動を行わない。
既存WAPの作業用テーブル作成・品質監査・公開と、ジョブの受付・排他・履歴を再利用する。
自動更新、変更検知、増分計算、依存先への連鎖実行はPhase 19.1には含めない。
追加サービス・依存ライブラリは導入しない。

定義は既存の `wap_models.json` にSQL・所有者・版・品質条件を保存する。
別のSQL定義台帳や登録ジョブの複製は作らず、`jobs.sqlite3` には実行時の定義と履歴を記録する。
両ファイルは既存のバックアップ対象で、復元後も自動実行しない。

## 操作と権限

管理者がTransformation画面で更新対象を登録・選択する。
モデル名は単純な識別子を小文字に正規化し、公開先は `iceberg.marts.<name>`、
作業用テーブルは `iceberg.sandbox.<name>` に固定する。
SQLは読取用SELECTまたはWITH、品質条件は最低行数とNULLを許さない列名を指定する。
保存してから「今すぐ更新」を実行する。実行中はジョブ履歴で状態とステップを確認できる。

- 一覧は管理者だけが取得でき、定義の更新・実行はその所有者に限定する。
- 編集・実行時は保存済みの版を照合する。古い版は再読込を要求する。
- 同名の従来WAPモデルを暗黙に引き継がない。登録済み定義を従来のWAP操作で上書きしない。
- 受付済みジョブがある場合は新規実行や定義編集を拒否し、待ち行列や自動再試行を作らない。
- 実行時には認証・権限を再検証し、受付時に保存したSQLと品質条件を使う。

## 更新と失敗の扱い

1. 保存したSELECTから作業用テーブルを全件作成する。
2. 作業用スナップショットを固定し、最低行数・NOT NULLと既存WAPの品質条件を確認する。
3. 合格した結果を既存WAPの単一テーブル置換処理で公開する。

品質不合格の場合は公開済みテーブルを保持する。公開前の既存WAPの列・行数退行チェックも維持する。
公開結果とSQLite履歴は単一トランザクションではないため、途中停止で結果が確定できなければ
`unknown` とし、実テーブルを確認するまで自動再実行しない。
最終実行状態と最終成功時刻を分けて表示する。

## API

| 操作 | API | 入力 |
|---|---|---|
| 一覧 | `GET /api/marts` | なし |
| 登録・編集 | `POST /api/marts/save` | `name`, `sql`, `min_rows`, `not_null`、編集時は`version` |
| 手動更新 | `POST /api/marts/run` | `name`, `version` |

`min_rows` は1以上の整数（既定1）、`not_null` は列名の配列（既定は空）。
空の公開結果は許可せず、既存テーブルからの大幅な行数減少に対する退行チェックも適用する。
一覧の `marts` と保存応答の `mart` には所有者・版・公開先・最新実行・最終成功時刻を含む。
手動更新は非同期ジョブの `run` を返し、既存の実行履歴APIで結果を確認する。

## 受入条件

登録のみではデータが変わらず、手動更新でSQLの結果を公開し、再実行で全件を置き換えること。
品質不合格で旧結果を保持し、権限・所有者・古い版・競合を拒否すること。
再起動・バックアップ復元で定義と履歴を保持し、中断した実行を自動再試行しないこと。
画面では保存と実行を区別し、未保存の入力や権限変更前の応答を誤って実行・表示しないこと。
