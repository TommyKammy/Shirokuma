# ローカルステージ（Phase 18.1〜18.3）

## 目的と構成

Workbenchを動かしているホストのフォルダに名前を付け、直下のファイルを選んで手動取込する。
既存のファイル読取・プレビュー・取込処理と、[登録ジョブ](registered_jobs.md)の
排他制御、バックグラウンド実行、処理履歴を利用する。
Phase 18.2では[スケジュール実行](scheduled_jobs.md)を使った定期確認と、内容単位の重複取込防止を追加する。
Phase 18.3では既存のテーブルエクスポートとジョブ実行を使い、ステージ内の `exports/` へ手動出力する。
設定と履歴は `SHIROKUMA_STATE_DIR/jobs.sqlite3` に保存する。
追加サービス、依存ライブラリ、監視スレッドは不要。

## 操作

1. 管理者として「データ取込」のローカルステージを開く。
2. ステージ名、ホスト上の絶対フォルダパス、取込先テーブル、取込方式、形式を登録する。
3. ステージを選び、一覧から1ファイルを選択してプレビューする。
4. ファイル名、取込先、方式、行数とサンプルを確認し、手動取込する。
5. ジョブの実行履歴で成否・取込件数を確認する。

ブラウザを開いているPCのフォルダ指定ではない。登録先はWorkbenchの実行ホストに存在する必要がある。
ブラウザからの一時アップロードは従来の取込フォームを利用する。

ステージには取込先と方式を固定する。`append` は追加、`replace` は選択ファイルで全件置換、
`upsert` は指定したキーによる更新・追加。`upsert` には入力列に存在するキーが必要。
ファイル一覧からの要求で取込先・方式・フォルダを上書きすることはできない。

## ファイルと権限

- 管理者だけがステージAPIを利用できる。他の管理者の設定は一覧で確認できるが、
  更新・ファイル一覧・プレビュー・取込は所有者だけが行える。
- 共有モードでは実行直前にもアカウントと管理者権限を再確認する。
- フォルダ直下のCSV、TSV、JSONL、NDJSON、JSON、Parquetを扱う。
  隠しファイル、未確定の拡張子、サブフォルダは取込対象にしない。
- 単一ファイルは25 MiBまで、ディレクトリ確認は1,000エントリまで。
  内容確認の対象ファイルは合計250 MiBまでとし、超える場合は明示的に拒否する。
  プレビューは最大10行を表示するが、既存の読取処理はファイル全体をメモリに保持する。
- 登録フォルダ外への参照、絶対ファイル名、親ディレクトリ参照を拒否する。
  標準ライブラリのパス解決を用い、外部のファイルアクセスサービスは追加しない。

一覧・プレビュー・受付では保存設定の版とファイルのサイズ・更新時刻を照合し、
実行時にも受付済みのファイル情報を照合する。変更された場合は一覧とプレビューをやり直す。
確認画面の取込先と方式にはプレビュー応答の設定を使い、別画面での設定変更による表示の食い違いを防ぐ。
これは内容の暗号学的な識別やファイルの排他ロックではない。
生成側は一時名で書き込み、完成してから確定名へ移動し、取込完了まで変更しないこと。

## 実行履歴と再起動

1回の取込は `trigger=stage`、`job_name=stage:<ステージ名>` の実行として記録する。
受付時のステージ設定と選択ファイルの情報を保存するため、後から設定を変更しても
実行中・過去の取込先や方式は変わらない。代理の登録ジョブやスケジュールは作成しない。

通常ジョブと同じ排他ロックを使用する。他のジョブが実行中なら競合として拒否し、待ち行列は作らない。
取込では既存の `atomic_append=True` を使用する。途中のworker喪失は `unknown` とし、自動再実行しない。
Icebergの更新とSQLiteの完了記録は別の処理なので、結果不明の場合は取込先を確認してから再実行を判断する。

Phase 18.2では、同じステージ・取込設定で成功した内容は、手動・自動のどちらでも再取込しない。
ファイル名変更や更新時刻だけの変更でも重複として扱う。

通常の再起動では設定と履歴を保持する。既存のバックアップ・復元にはSQLiteの設定と履歴が含まれるが、
登録元フォルダのファイルは含まれない。復元先ではフォルダと原本を別途用意する。
フォルダや原本が存在しない場合は明示的に失敗し、作成や代替ファイルの探索は行わない。

## 定期確認と自動取込（Phase 18.2）

ステージを選び、確認間隔を1〜10,080分で設定して有効にする。初期状態は無効。
Workbenchの既存スケジューラが予定を確認するため、追加の監視サービスや外部cronは不要。
「今すぐ確認・取込」でも同じ処理を開始できる。

- 自動・一括取込は `append` と `upsert` に対応する。`replace` は単一ファイルの手動取込で使用する。
  複数ファイルの連続置換によって最後のファイルだけが残る動作は行わない。
- 直下の対象ファイルから、更新後30秒以上経過した未処理の内容を名前順に最大10件取り込む。
  残りは次回の確認対象になる。30秒は生成完了の保証ではないため、一時名から確定名へ移す運用は引き続き必要。
- ブラウザを閉じても実行する。Workbenchの停止中・ホストのスリープ中は実行しない。
- 通常ジョブと同じ排他制御を使う。競合時や予定から60秒以上遅れた場合はその予定をスキップし、追いつき実行はしない。
- 予定を停止すると将来の確認を止める。すでに受け付けた処理は中断しない。
  ステージ設定の保存時にも予定を停止するため、取込先や方式の変更後は確認して再度有効にする。
- 保存した所有者・管理者権限・認証モードを発火前と各ファイルの処理前に確認する。
  権限失効や認証モードの変更時は実行を許可しない。
- 通常再起動では予定と処理済み台帳を保持する。バックアップから復元した予定はすべて無効にする。

## 重複判定と再試行

重複判定には、取り込むバイト列のSHA256とステージ・取込設定を用いる。
同じ内容でも別ステージや別の取込先・方式などは別処理となる。
これはファイル全体の重複判定であり、行単位の重複排除ではない。
既存ファイルに行を追記すると別内容となり、`append` では元の行を含むファイル全体を追加する。
差分ファイルを置くか、更新対象のキーがある場合は `upsert` を利用する。

取込の受付をSQLiteに記録してからデータを書き込み、成功後に処理済みとする。
取込呼出し以降に結果を確定できない場合は `unknown` を残し、自動再試行しない。
ファイル一覧とジョブ履歴で状態を確認できる。
失敗・結果不明の手動再試行には明示的な確認が必要で、すでに反映済みなら行が重複し得る。
成功済みファイルを強制的に再取込する操作は提供しない。

SQLiteとIcebergをまたぐ単一トランザクションや、障害をまたぐexactly-onceは保証しない。
台帳だけを過去へ戻した場合も、倉庫への反映状況を確認してから予定を有効にする。

Phase 18.1の取込履歴には内容の識別情報がないため、過去の取込を自動的に処理済みとして推定しない。
旧履歴のあるステージは閲覧・プレビュー・予定停止を引き続き利用できるが、新しい取込と予定有効化は拒否する。
以前の取込結果を確認して処理済みファイルを対象フォルダから移し、新しいステージ名で登録して再開する。

## ステージへのファイル出力（Phase 18.3）

所有するステージを選び、出力元テーブル・形式・ファイル名を指定して手動実行する。
出力元テーブルはステージの取込先とは別に指定できる。任意SQL、複数ファイルへの分割、
出力のスケジュール、上書き、ファイル削除・ブラウザダウンロードは今回追加しない。

- 出力先は登録フォルダ内の固定 `exports/` 子フォルダ。初回実行時に作成する。
  通常の取込は登録フォルダ直下だけを調べるため、生成した出力を自動で再取込しない。
  `exports/` 自体を別の取込ステージとして登録した場合は、その明示的な設定に従う。
- CSV、JSONL、Parquetに対応し、拡張子は形式と一致させる。直接ファイル名だけを受け付ける。
  ParquetにはWorkbenchを実行するPythonの既存任意依存 `pyarrow` が必要。未導入なら明示的に失敗する。
  既存名は上書きしない。再度出力する場合は新しい名前を指定する。
- テーブル全件を対象に、最大100,000行・完成ファイル25 MiBまでとする。超過時は一部を公開せず失敗する。
  件数取得とデータ取得は別クエリなので、両者の件数が一致しない場合も公開しない。
  テーブル全体の履歴やIcebergメタデータを保存するバックアップ機能ではない。
- 出力一覧の確認は1,000エントリまで。超える場合は一部だけの一覧を返さず、明示的に失敗する。
- 既存エクスポートと同様に、取得結果と生成ファイルをメモリに保持する。上限は出力の受付条件であり、
  処理中のメモリ使用量を25 MiBに制限するものではない。
- 形式の意味も既存エクスポートに従う。CSVではNULLと空文字を区別できない。
  Parquetの型は取得した値から推定するため、SQLの型・DECIMAL精度・空列の型の完全な保持は保証しない。
  JSONLにもTrinoから取得した値の表現を用いる。型と精度の完全な往復変換を目的としない。

ステージ所有者かつ管理者だけが出力・出力一覧を利用できる。受付、実行開始、公開直前に設定の版と権限を確認し、
途中で保存設定や権限が変われば公開しない。画面に古い設定が残っている場合は、ステージ一覧を更新して確認し直す。

既存ジョブと同じ排他・履歴を使い、待ち行列や代理ジョブは追加しない。
同じ出力フォルダ内の隠し一時ファイルに書き込み、検証成功後に非上書きで確定名を公開する。
出力一覧は確定ファイルだけを表示する。通常の失敗では一時ファイルを削除する。
強制終了では隠し一時ファイルが残ることがあるが、自動取込や確定ファイル一覧の対象にはならない。

ファイル公開とSQLiteの成功記録は単一トランザクションではない。公開後に処理が失われた場合は `unknown` とし、
再起動で自動再実行しない。出力一覧とファイルの内容を確認してから、再出力の要否を判断する。
バックアップ対象はSQLiteの設定・実行履歴であり、`exports/` の実ファイルは別途保存する。

## HTTP API

すべて管理者限定。利用者とロールは既存HTTP認証で決定する。

| Method / path | 入力 | 結果 |
|---|---|---|
| `GET /api/stages` | なし | `stages` 一覧 |
| `POST /api/stages/save` | `name`, `directory`, `table`, `mode`, `format`, 任意の `key` | 保存した `stage` |
| `POST /api/stages/files` | `name` | `files`、上限情報 |
| `POST /api/stages/preview` | `name`, `file`, `version` | 列、行数、サンプル、ファイル版、確認対象の `stage` 設定 |
| `POST /api/stages/import` | `name`, `file`, `version` | HTTP 202、`run` |
| `POST /api/stages/scan` | `name`, `version` | HTTP 202、確認・取込の `run` |
| `POST /api/stages/schedule` | `name`, `every_minutes`, `enabled`、有効化時の `version` | 保存した `schedule` |
| `POST /api/stages/export` | `name`, `version`, `table`, `format`, `file` | HTTP 202、出力の `run` |
| `POST /api/stages/exports` | `name` | 出力先 `directory`、確定 `files`、`limits` |

`version` はサーバーの一覧・プレビューが返した値をそのまま渡す。
履歴と詳細は既存の `/api/jobs/runs` と `/api/jobs/detail` を利用する。
予定の停止だけなら `{"name":"daily_orders","enabled":false}` を送る。
確認・取込の開始と予定有効化の `version` には、ステージ一覧の `updated_at` を渡す。
ファイル出力の `version` にも同じ `updated_at` を渡す。
画面に表示した設定が別画面で変更されていた場合は拒否し、設定の再確認を必要とする。
予定停止は古い画面からでも実行できる。
失敗・結果不明の手動再試行は `/api/stages/import` に `"retry":true` を追加する。
ステージの予定は内部で `stage:<名前>` として既存の予定台帳に保存し、代理の登録ジョブは作成しない。
