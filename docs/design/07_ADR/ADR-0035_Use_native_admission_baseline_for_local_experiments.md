# Use native admission baseline for local experiments

## Context

The autonomous local experiment uses the dedicated `mac-studio-solo` k3s lab
under [ADR-0034](ADR-0034_Use_autonomous_local_experimental_development.md).
On 2026-09-17 the running k3s `v1.33.4+k3s1` exposed native
`admissionregistration.k8s.io/v1` ValidatingAdmissionPolicy and Binding APIs,
but had no Kyverno CRDs or additional admission policy/webhook objects.
Repository policy tests therefore did not establish live admission enforcement.

The retained Kyverno v1.18.2 / chart 3.8.2 inventory records historically blocked
ARM64 controller images. It is not current evidence of a clean upstream release.
Installing these controllers is unnecessary for the local baseline because
the existing seven `policies/kyverno/baseline.yaml` rules already use CEL.

## Decision

Use a namespace-limited native ValidatingAdmissionPolicy bridge in this local
experiment. This is an implementation choice within the standing local policy
authorization, not a new production or upstream-image acceptance decision.

- Reuse the existing seven baseline rule meanings and matching resource
  types: privilege, host namespaces, hostPath, resources, hostPort, immutable
  untagged digest syntax, and public Service/Ingress restrictions.
- Project them into eight native policies: split the public-exposure rule into
  Service and Ingress policies. The native API type-checks each matched kind;
  the original combined expression references Service-only fields and produced
  Ingress type warnings. The other six rules retain their source expressions.
  Keep static type checking enabled and retain the original Kyverno source.
- Use dedicated `shirokuma-local-*` names and ownership labels. Both policy and
  binding restrict matching to `shirokuma-dev`; use `failurePolicy: Fail` and
  binding action `Deny`.
- Check the fixed loopback cluster scope, server-dry-run manifests, and verify
  policy generation/type-checking without warnings before activating bindings.
  Refuse conflicting ownership or unexpected existing content.
- Test an allowed private Pod/Service and explicit deny cases using server-side
  dry-run; verify each denial is attributable to the expected local policy.
  Inspect retained workload compatibility before activation. Do not roll,
  restart, replace or delete retained Pods to demonstrate this baseline.
- Keep the Kyverno mainline policy files, blocked inventories, expiration dates,
  supply-chain verdicts and external-delivery requirements unchanged.

The bridge protects actual Pod admission, including the subresources selected
by the baseline, plus Services/Ingresses. Native VAP does not provide Kyverno
autogenerated controller-template validation or background policy reports. A
Deployment can be accepted while its future Pod is denied; the experiment does
not claim controller-template parity.

## Consequences and limits

No new controller, image, registry publication, resident memory allocation or
data volume is needed. The implementation reuses the existing API server and
does not broaden the namespace boundary. A digest-syntax rule does not prove
that an image is approved, signed or free of vulnerabilities. This bridge is
neither RBAC/OPA authorization nor continuous runtime enforcement.

Policy changes are recorded with local input hashes, object identities and
allow/deny evidence. Safe withdrawal removes only the owned local bindings
after identity checks; it does not remove retained workloads or unrelated
policies. Keep the policy objects/evidence for inspection. Later changes to the
mainline Kyverno path require their own live verification rather than rewriting
the old security history.

Functional results and reproducible commands are recorded in
[Local Experiment Milestones](../06_WorkPackages/061_Local_Experiment_Milestones.md).
